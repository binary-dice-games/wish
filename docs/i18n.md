# Internationalization (i18n)

wish templates can be translated. A template string whose **whole value**
starts with `$$` is a translation key: `"label": "$$TAIL_FOLLOW"` shows the
translation of `TAIL_FOLLOW` in the session's language. Any other string,
including one with `$$` in the middle, is left as it is.

```json
{ "type": "Button", "label": "$$APP_SAVE" }
```

Keys are replaced **after** the JSON/YAML is parsed, one string value at a
time, so a translation can contain quotes, colons, braces or newlines
without breaking the template. Detection is a two-character prefix check,
not a regex.

## Translation files

One file per language, named `<lang>.lang` (`en.lang`, `es.lang`, ...),
UTF-8, one `KEY = value` per line:

```ini
# Comments start with # or ;
APP_SAVE = Guardar
APP_HINT = Línea 1\nLínea 2
```

- Key and value are trimmed; the first `=` splits them, so values may contain `=`.
- Escapes in values: `\n`, `\t`, `\\`.
- A later duplicate key wins; lines without `=` are ignored.

## Lookup order

1. The selected language's file (`es.lang`).
2. The English file (`en.lang`), the fallback for every language.
3. The bare key (`APP_SAVE`), so a missing translation is visible in the UI.

Ship an `en.lang` for every module that uses keys.

## Choosing the language

| Where | How |
|-------|-----|
| CLI | `wish client --run=tail --lang=es`, `wish standalone --lang=es`; `wish server --lang=es` sets the default for every session |
| C++ client | `client.set_language("es")` |
| C ABI | `wish_set_language(c, "es")` |
| Bindings | `set_language("es")` (Python, C++ header, Rust), `SetLanguage` (C#, Go), `setLanguage` (Android) |
| Server code | `server::set_default_language("es")` before `start()` |

Language codes may contain only letters, digits, `-` and `_` (`es`,
`pt-BR`); anything else is rejected. The language affects UI built after it
is set. Existing widgets keep their text.

## Server-side tools and forms

The server looks up a tool's translations in the session sandbox, at
`res/<org>/<collection>/<name>/i18n/<lang>.lang`. A module ships them as
embedded resources:

```
modules/bdg/desktop/tail/
  resources/embedded/i18n/en.lang
  resources/embedded/i18n/es.lang
```

The embedded-resource build step packs these files into the binary. Every
session extracts them under `res/`. The built-in forms (`MessageBox`
buttons) use the top-level `resources/embedded/i18n/`, which is `res/i18n/`
at runtime.

In a `common::tool_form`, set the module prefix in the constructor. After
that, `build_window()` translates the layout, and `tr()` translates strings
built in code:

```cpp
tail::tail(dynamic&& base) : tool_form(std::move(base)) {
  i18n_prefix_ = "bdg/desktop/tail";
}
// ...
status_label_ptr_["text"_key] = tr("$$TAIL_INVALID_REGEX") + " " + e.what();
```

`tr()` keeps the map it loads the first time it is called, so it also works
from `on_event()`. A plain `wish::form` can call `tr(text, "<org>/<coll>/<name>")`
during dispatch. Other code can call
`import_json(layout, sess().translations_for(prefix).get())` or
`context::translations_for()` directly.

## Client-side templates

Templates a client registers are translated **on the client**, with a map
the client provides. `register_template_from_json`/`_yaml` (C++) and
`wish_register_template` (C ABI and every binding) apply it:

```cpp
auto es = wish::load_translations_file("i18n/es.lang").value_or(wish::translation_map{});
if (auto en = wish::load_translations_file("i18n/en.lang"))
  es.set_fallback(std::make_shared<wish::translation_map>(std::move(*en)));
client.set_translations(std::move(es));
client.register_template_from_json("ui"_key, R"({"type":"Window","title":"$$APP_TITLE"})").get();
std::string msg = client.translate("$$APP_SAVED");  // strings built at run time
```

```python
c.load_translations("i18n/es.lang", "i18n/en.lang")   # or set_translations(text, fallback)
c.register_template("ui", '{"type": "Window", "title": "$$APP_TITLE"}')
c.translate("$$APP_SAVED")
```

C: `wish_set_translations(c, es_text, en_text)`, then
`wish_translate(c, "$$KEY", &out)` (release `out` with `bison_free_string()`).

`register_template(name, dynamic)`, which takes a tree you built yourself,
is not translated. Client-side module code can read the session's language
with `wish_app_host::language()`.

## Converting an existing module

1. Replace each user-facing string in the layout with a `"$$<MODULE>_<NAME>"`
   key. Leave ids (`"##..."`), icons and paths alone.
2. Put the English text in `resources/embedded/i18n/en.lang`, and the other
   languages next to it.
3. In the form constructor, set `i18n_prefix_ = "<org>/<collection>/<name>"`.
   Wrap strings built in C++ with `tr("$$KEY")`.
4. Add a test that sets the server's default language and checks a label
   (see `TailLanguageTest` in `tests/test_tail.cpp`).

ImGui uses a widget's label as part of its id, so a translated label gives
the widget a different id in each language. This is harmless, but automation
scripts that match widgets by label text must use the translated text.
