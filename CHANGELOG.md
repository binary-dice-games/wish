# Changelog

All notable user-facing changes to wish are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `dbg` module: selectable debug backend via `wish client --run=dbg -- --backend <native|python>`. The new **`python`** backend (`python_debug_backend`) debugs a Python process by driving Microsoft's `debugpy` over the Debug Adapter Protocol — attach, pause/resume, step into/over/out, file:line breakpoints, thread list, call stack, and Watch expression evaluation, plus debuggee output forwarded to the Output window. It attaches by PID (`python -m debugpy.adapter` injects `debugpy`, needs `debugpy` installed and OS support for the injector), or connects straight to a `debugpy` server the target already started with `debugpy.listen((host, port))` via `-- --backend python --connect host:port`. `$WISH_DBG_PYTHON` / `$WISH_DBG_DAP_CONNECT` override the interpreter / endpoint. Cross-platform (Windows included).

- `posix_debug_backend` (Linux/macOS client-side implementation of the `dbg` module's `debug_backend` seam): drives a child `gdb --interpreter=mi` (or `lldb-mi`) process over the GDB/MI protocol — attach/detach, pause/resume, step into/over/out, file:line breakpoints, thread list, call stack, and simple local-variable Watch evaluation (value via `-data-evaluate-expression`, type via `whatis`), plus debuggee output forwarded to the Output window. The debugger binary is found on `PATH` (`gdb`, then `lldb-mi`) or forced with `$WISH_DBG_DEBUGGER`. `wish client --run=dbg` now has a working backend on Linux and macOS, not just Windows; the module is no longer Windows-only.

- `DockLayout` / `DockSplit` / `DockArea` elements: a UI (a server-side `wish::form` via `form::set_default_dock_layout()`, or a client-registered template descriptor) can declare the initial docking arrangement of its windows. The renderer realizes the split tree via ImGui's DockBuilder on first run, after the element's `version` increases, or when a sibling tool sharing the dockspace has rebuilt it — otherwise it leaves the arrangement to `imgui.ini` like any user drag. Build the tree from C++ with the `bdg::wish::dock::` helpers in `src/ui/dock_layout_spec.hpp`. See [docs/dock-layout.md](docs/dock-layout.md).
- `DockSpaceViewport` gains a `title` field: the user-facing name shown on the tab/title bar when `embedded`, distinct from `id` (which stays purely internal -- the DockSpace/DockBuilder identity and any nested `DockLayout.target` are still derived from `id` alone). `dock::viewport(id, title, layout(...))` now takes the display name as its second argument; `docker`/`kubectl`/`git`/`dbg` now show "Docker"/"Kubectl"/"Git"/"Debugger" instead of their internal `*_dock` ids.
- `DockSpaceViewport` gains an `embedded` field: when true, it renders as an ordinary dockable window (one tile among its siblings, docking into whatever dockspace is already ambient on first use) carrying its own nested `ImGui::DockSpace()`, instead of the fullscreen, non-dockable host chrome. Combined with a `DockLayout` whose `target` names that same id, an app's whole window set can be wrapped into one isolated, nested dock tree that a sibling app sharing the same outer host dockspace can never rearrange or evict — build one with `bdg::wish::dock::viewport(id, layout(...))`. `docker`, `kubectl`, `git`, and `dbg` all now opt into this. See [docs/dock-layout.md](docs/dock-layout.md).
- `Plot` gains `legend_location` (`ImPlotLocation`) and `legend_flags` (`ImPlotLegendFlags`) fields for placing the legend — e.g. `legend_location: "South"` + `legend_flags: "Outside"` renders it below the plot instead of over the trace.
- `docker` module: new **Stats** window — live `docker stats` CPU % and memory % history graphs (one `PlotLine` per running container, capped at the 15 busiest, plus a "Total" line) and a current-values table (Name / CPU % / Mem % / Mem Usage). Sampled by a background poll thread every ~3 s; these polls are not shown in the Console window.
- `kubectl` module: new **Top** window — live `kubectl top` graphs: pod CPU (millicores) and pod memory (MiB) with a per-pod line (top 15) plus "Total", node CPU % and node memory % with a per-node line plus "Cluster avg", and current-values tables for pods and nodes. Sampled by a background poll thread every ~10 s; these polls are not shown in the Console window. Shows a status message when `kubectl top` is unavailable (e.g. metrics-server not installed).

- `kubectl` module (`WISH_MODULE_BDG_DEV_KUBECTL`, off by default): a Kubernetes-dashboard-style GUI frontend for the local `kubectl` CLI, run with `wish client --run=kubectl`. Ships seven dockable windows — Pods, Deployments, Services, Nodes, Logs, Describe, and a Console that traces every `kubectl` command the module runs (command, exit code, output; green/red) — each list window a table with a per-row `...` action menu (pod delete; deployment rollout-restart/delete; service delete; node cordon/uncordon/drain; logs; describe), plus name/namespace and pod-phase filters, and a `MessageBox` confirm on delete/drain. All `kubectl` invocation is client-side against the current kubeconfig context; refresh is manual (Refresh button + after every action), no background polling.
- `docker` module (`WISH_MODULE_BDG_DEV_DOCKER`, off by default): a Docker Desktop-style GUI frontend for the local `docker` CLI, run with `wish client --run=docker`. Ships seven dockable windows — Containers, Images, Volumes, Networks, Logs, Inspect, and a Console that traces every `docker` command the module runs (command, exit code, output; green/red) — each list window a table with a state-aware per-row `...` action menu (start/stop/restart/pause/unpause/kill/remove, image run/remove, volume/network remove, inspect), plus name/image and running/stopped container filters, inline pull-image and create-volume fields, and a `MessageBox` confirm on stop/kill/remove/prune. All `docker` invocation is client-side; refresh is manual (Refresh button + after every action), no background polling.
- `wish server` and `wish standalone` gain a `--allow_absolute_paths` flag, wiring the CLI up to the existing `wish::server`/`wish::standalone::set_allow_absolute_paths()` library setters. Required for the `dbg` module's Source window (and any other absolute-path file widget) to actually show file contents — see Fixed below.
- `wish_server_set_log_level()` (C ABI) and `set_log_level()` / `SetLogLevel()` (C++, Python, C# bindings): set the server log verbosity by name.
- Rust (`bindings/rust/`) and Go (`bindings/go/`) client language bindings for the wish client C ABI.
- Rust (`bindings/rust/wish-server/`) and Go (`bindings/go/wishserver/`) server language bindings: host and render a real wish session over `wish_server_c.h` (`Server`, `Params`).
- `examples/ui/json/` and `examples/ui/yaml/` — standalone editor example UIs, one file per tab of the `demo` app, in both formats.
- `tooltip` field on every UI element: when non-empty, its text is shown via `ImGui::SetTooltip()` while the element is hovered.
- `VerticalLayout` (and `TabItem`) gain a `scroll` boolean field: when true, the layout's children render inside a vertically-scrolling child region sized to the space the layout was given, so overflowing content scrolls instead of clipping the enclosing window.
- `TextEditor` gains `breakpoint_lines` (int array, 1-based) and `current_line` (int, 1-based, 0 = none) fields, rendering a breakpoint dot / current-line arrow in the gutter, and a `"line_context_menu"` event (`{line, has_breakpoint}`) emitted on a gutter right-click.
- `dbg` module (`WISH_MODULE_BDG_DEV_DBG`, off by default): Visual-Studio-style debugger GUI frontend, run with `wish client --run=dbg`. Ships six dockable windows — Source, Threads, Call Stack, Watch, Breakpoints, Output — driven by server-side `update_*` RMI methods against a client-side `debug_backend` seam. The Source window opens a `TextEditor` tab per file (double-clicking a Call Stack frame with no open tab emits `open_file_requested`; selecting a frame opens/focuses its file); right-clicking a line number toggles a breakpoint end-to-end (`line_context_menu` → `toggle_breakpoint_requested` → `win32_debug_backend` `INT3` patch/restore → `update_breakpoints`/`update_source` rebuild). Threads/Call Stack rows are wired end-to-end (row click emits `select_thread_requested`/`select_frame_requested`). Step Into/Over/Out buttons emit `step_requested` end-to-end. The Watch window resolves a typed expression against the selected frame's simple local variables (name/value/type) and refreshes on every stop or frame selection. The Output window traces attach/stop/exception events and debuggee `OutputDebugString` calls, FIFO-capped at 500 rows and colour-coded by severity (info/warn/error). The client runner wires all `*_requested` events to a real `win32_debug_backend` on Windows.
- `win32_debug_backend` (Windows-only client-side implementation of the `dbg` module's `debug_backend` seam): attach/detach a real process via the Win32 debug API (`DebugActiveProcess`/`WaitForDebugEvent`/`ContinueDebugEvent` on a dedicated debug thread), pause/resume, step into/over/out (single-step for Into, a temporary return-address breakpoint for Over/Out), and file:line software breakpoints (INT3 patch/restore) resolved via DbgHelp, including stop reporting on `STATUS_BREAKPOINT` (original byte restored, IP rewound) and on unexpected first-chance exceptions. Resolves Watch expressions to local-variable values via DbgHelp symbol enumeration (scalar types decoded, including intrinsic types like `int`/`bool`/`float` that have no symbol name of their own; others shown as a raw hex dump; register-resident locals reported as unavailable), and forwards debuggee `OutputDebugString`/`OutputDebugStringW` output to the Output window. Now wired into the `dbg` module's client runner (`wish client --run=dbg` on Windows).

### Fixed

- `DockLayout`: manually rearranging windows was effectively impossible once a `DockLayout` was in use (e.g. in `docker`/`kubectl`) — dragging a window by its title bar or tab could snap the whole arrangement back to the default mid-drag or crash right after dropping, floating a single window out standalone reset the *entire* arrangement, and running one tool after another that shares the same host dockspace (e.g. `docker`, then `git`, then `docker` again) could reset the first tool's arrangement back to its hard-coded default on its next run. All of these came from the same root cause: the reapply check tried to infer "did a sibling app rebuild the shared dockspace" from transient or displaced window docking state, and reacted to that by rebuilding the coded default — discarding whatever the user had arranged. It now applies a layout at most once per `version`, full stop; once applied, nothing (a drag, a float-out, a sibling app rebuilding the shared dockspace) ever triggers another rebuild, matching how any other manually-arranged window is left to `imgui.ini` from then on.
- `CollapsingHeader` could not be collapsed/expanded by clicking unless the app wrote the new state back onto its `open` field in the `toggled` handler. The renderer now writes `open` back on toggle itself (matching `Checkbox`/`Slider`), so clicks work without app-side wiring.
- `dbg` module: `win32_debug_backend::detach()` could kill the debuggee with an unhandled single-step exception if called while stopped right on a just-hit breakpoint (e.g. Detach clicked, or evaluating a Watch expression, before Continue/Step); it now skips arming the trap flag it would never get a chance to service.
- `dbg` module: after attaching, the toolbar's Detach/Pause/Continue/Step buttons stayed disabled forever (`set_run_state` updated only the state label, never button enablement) and the Call Stack/Watch windows never populated on the first stop (their staleness guards required a prior manual Threads/Call Stack row click before accepting any snapshot). `set_run_state` now enables/disables each button per DESIGN.md's documented contract, and the first automatic snapshot after a stop is adopted as the current selection instead of being dropped. The client (`dbg_source`) also now synchronizes every RMI call instead of discarding its result, matching `docker`/`git`/`kubectl`'s convention, so a server-side error surfaces to the client instead of failing silently.
- `dbg` module: on Windows, attaching to a real, already-running external process (as opposed to the test fixture's self-spawned child) silently failed -- the run state stayed stuck on "detached" and every panel (Source, Threads, Call Stack, Watch, Breakpoints, Output) stayed empty, with no error anywhere. `win32_debug_backend::attach()` called `DebugActiveProcess` with no `SeDebugPrivilege` elevation on its own process token, which that API can require to attach to a process it didn't itself spawn; a failure was also never surfaced (no `GetLastError()` capture, no Output-window message). `attach()` now enables `SeDebugPrivilege` before attaching and logs (via the Output window) a warning if that fails and an error with the OS error code if `DebugActiveProcess` itself then fails, instead of failing silently.
- `dbg` module: on Windows, every panel (Source, Threads, Call Stack, Watch, Breakpoints, Output) could come up completely empty right after attaching, with only the run-state label showing "paused". `win32_debug_backend` called DbgHelp (`SymInitialize`/`SymLoadModuleEx`/`SymFromAddr`/`SymGetLineFromAddr64`/`StackWalk64`/`SymEnumSymbols`/`SymEnumLines`) from two different threads at once with no synchronization -- DbgHelp is single-threaded per process handle, so the very next debug-thread call after attach (populating Threads) could race against the attaching thread's own concurrent DbgHelp use and silently stall, aborting every subsequent panel update for that stop. All DbgHelp access is now serialized behind a dedicated mutex.
- `dbg` module: Threads, Call Stack, Watch, Breakpoints, and Output tables still rendered empty after a real attach even once correct data reached the client (`get_tree()` showed the rows; the screen did not) -- each table's row-rebuild rebuilt the underlying data directly without refreshing the renderer's cached child-render order, so newly inserted rows were never drawn. All five now refresh that order after rebuilding, and the tables render correctly.
- `dbg` module: the Source window's per-file tab always rendered empty, even though the tab itself was created correctly with the right label. Source files are opened by their absolute on-disk path (from the debug backend/PDB), but `TextEditor`'s renderer rejects absolute paths unless the server was started with `set_allow_absolute_paths(true)` — a setting no `wish` CLI flag ever exposed, so this was unfixable by any actual user of the tool. Fixed by adding `--allow_absolute_paths` to `wish server`/`wish standalone` (see Added above); pass it when running the `dbg` module for the Source window to show real content.
- `DockLayout`: an app switching its layout to target a new, named dockspace (e.g. opting into `DockSpaceViewport.embedded`/`dock::viewport(...)`) while keeping the same windows and `version` left every one of its windows undocked on launch. The persisted "already applied" record was keyed only by the window-path list, not the target dockspace, so the unchanged version looked like a no-op re-run; its one fallback (reapply if the target node doesn't exist) never caught it either, because `ImGui::DockSpace()` auto-creates an empty node at a new id before the check runs. The target dockspace is now folded into that persisted identity, so a changed target is treated as a layout that has never been applied.
- `DockLayout`: a session's windows could still all end up crammed into one shared tabbed node instead of the intended split, even on a completely fresh run with no `imgui.ini` (e.g. `docker` standalone). `session::top_level_objects` iterates in arbitrary, unordered-map order, so a session's own windows could render (and resolve their first-ever dock placement) before that session's `DockLayout`/`DockSpaceViewport` got a chance to run `DockBuilderDockWindow()` in the same frame; ImGui then pruned the freshly-built, still-unhosted split nodes at end of frame, permanently collapsing the layout. Both the standalone and server render loops now always render a session's `DockLayout`/`DockSpaceViewport` top-levels before its other top-levels each frame, regardless of iteration order. See [docs/dock-layout.md](docs/dock-layout.md).
- `dbg` module: clicking a Call Stack frame opened the right file in the Source window but never scrolled to the current line, leaving the view at the top of the file with only the gutter arrow marking the real location. The `TextEditor` renderer now scrolls to keep the current execution line centered whenever it changes.
- `dbg` module: selecting a different thread in the Threads window never updated the Call Stack window — it kept showing whichever thread's callstack was last pushed. On Windows, the Win32 debug API only actually halts the thread that raised the current debug event; every other thread keeps running, so `win32_debug_backend` now suspends every thread on a stop (and resumes them on continue) instead of only the reporting thread, matching `get_threads()`'s reported "suspended" state and giving `get_callstack()` a stable snapshot for any thread the user selects.
- `dbg` module: stepping Into/Over/Out could leave the Call Stack and Watch windows showing stale data from before the step, if a specific thread or Call Stack frame had been selected beforehand. `set_run_state("paused")` — sent at the start of every stop — now resets that selection so each step's fresh snapshot is always adopted instead of possibly being dropped as stale.
- `dbg` module: adding a Watch expression before the debuggee had ever stopped silently failed to appear in the Watch table. `on_add_watch_requested` now always re-evaluates and pushes the watch table, instead of only when a current frame was already selected.
- `dbg` module: the Output window's "attach at", "step at", "pause at", … messages showed `:0` instead of a real filename and line whenever the debugger backend had no line info for the stop address (e.g. a loader thunk on attach, or the ntdll thread `DebugBreakProcess()` uses for Pause) — these messages now show just the reason instead of the misleading `:0`. Also corrected a one-byte INT3-overshoot on the Pause stop address (the same fix already applied to real breakpoint hits), for internal consistency even though Pause's break address itself is never resolvable to the debuggee's own source.

### Changed

- `docker`, `kubectl`, and `git` modules: the windows open pre-arranged into a docked layout on the first run instead of as floating windows — `docker`/`kubectl` show a tabbed list column over a Console strip on the left with Logs + Inspect/Describe tabbed on the right; `git` fills the left with the commit graph over a Log strip and stacks Files over Diff on the right. Rearranging and restarting keeps your own arrangement.
- `docker` / `kubectl` modules: list, log, and console tables now scroll both horizontally and vertically; the Inspect / Describe views no longer clip long lines.
- `editor` module: loads `.yaml` / `.yml` UI files in addition to JSON, selected by file extension, with full feature parity — YAML syntax highlighting, schema-aware autocomplete, and the cursor-tracked Help panel / preview highlight all work for YAML sources.
- `editor` module: closing with unsaved edits now uses a real modal `MessageBox` ("Save changes … before closing?", Yes / No / Cancel) instead of an inline panel.
- `TextEditor`: new `"yaml"` value for the `language` field (YAML syntax highlighting); `wish_ui_schema` autocomplete now also applies when `language` is `"yaml"`.
- `CollapsingHeader`'s `open` field is now server-authoritative: it is forced into ImGui every frame (`ImGuiCond_Always`) instead of being applied once and then owned by ImGui. Update the field in the `toggled` handler to keep the header responsive to clicks. This fixes a spurious open/close oscillation when a `CollapsingHeader`'s subtree is rebuilt every frame.
- `--verbose` is now a verbosity level (`none` | `fatal` | `error` | `warning` | `info` | `trace`, default `none`) instead of an on/off flag. RMI trace lines and session lifecycle lines in `wish_logs/server.log` (and mirrored to stdout) are produced only at `info` and above; decoded call payloads (`args=`, `set` values, response bodies) only at `trace`. `fatal`/`error`/`warning` only raise the severity floor for client log messages. At `none` (the default) the server log stays silent and the trace string is never built.
- `wish_server_set_verbose()` / binding `set_verbose(bool)` are deprecated: `true` now maps to log level `trace`, `false` to `none`.
- Server render loop: reduced per-frame CPU and heap-allocation churn — zero-copy string field access on the render/measure/arrange hot path, `ui_element::for_each_child_ordered()` no longer allocates per call, cached MenuBar-child detection, and fewer per-frame map/style copies in the render loop. No behavior change.
- Read-only RMI requests (`get` / `describe` / `dictionary` / `help`) no longer schedule redraw frames — a client polling widget values with `get` no longer holds a session at full framerate. Mutating requests (`set`, `call`, `instantiate`, …) are unaffected.
